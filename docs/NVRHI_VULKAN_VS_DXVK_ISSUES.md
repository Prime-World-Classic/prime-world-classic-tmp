# Сравнение RenderDoc-капч NVRHI(Vulkan) ↔ DXVK: найденные проблемы

Разбор двух капч одного и того же клиента (D3D9-слой `d3d9`), сделанный поштучно по
событиям. Цель — найти события, которые в NVRHI/Vulkan приводят к расхождению
картинки, а в DXVK — нет.

С 2026-10-25 в документе две пачки доказательств: капчи RenderDoc (Проблемы 1–9,
разбор ниже по событиям) и попарный разбор кадров A/B + чтение кода (Проблемы
10–12). Класс доказательств указан в каждой проблеме — выводы по кадрам слабее
капчи, они не называют GPU-событие, а только связку «код → картинка».

# Проблема 1 (критическая). Карта теней рисуется viewport/scissor 1024×768 вместо 2048×2048

Заполняется ровно **1/4 площади** карты теней (по X — 1/2, по Y — 768/2048 = 3/8),
остальные 3/4 карты в кадре NVRHI **не записываются никогда**. DXVK пишет всю карту.

## События Vulkan

Проход карты теней: `vkCmdBeginRendering` area=`2048x2048` offset=`(0,0)`,
аттачменты — color `view#36431 → img#36424`, depth `view#36432 → img#36422`.
Проходов несколько (`passn` 48, 62, 74, …), суммарно **107 `vkCmdDrawIndexed`,
400 767 индексов, ev54 … ev999**. Состояние на все 107 одинаковое:

```
ev54  vkCmdDrawIndexed indexCount=978 instanceCount=1 firstIndex=0 vertexOffset=0
      pass ev… area=2048x2048 off=(0,0)
      VP (0, 768, 1024, -768)  SC (0, 0, 1024, 768)      <-- ОШИБКА: размер чужой цели
```

Последовательность всех `vkCmdSetViewport`/`vkCmdSetScissor` кадра (9 пар) —
**ни одна не 2048×2048**:

```
VP(0,205,205,-205)   SC(0,0,205,205)    -> draw#0   ev25   img#29351
VP(0,768,1024,-768)  SC(0,0,1024,768)   -> draw#2   ev54   img#36424  (КАРТА ТЕНЕЙ)
VP(0,256,256,-256)   SC(0,0,256,256)    -> draw#227 ev1883 img#182
VP(0,384,512,-384)   SC(0,0,512,384)    -> draw#229 ev1907 img#190
VP(0,768,1024,-768)  SC(0,0,1024,768)   -> draw#318 ev2435 img#170
VP(0,192,256,-192)   SC(0,0,256,192)    -> draw#347 ev2797 img#206
VP(0,768,1024,-768)  SC(0,0,1024,768)   -> draw#350 ev2830 img#172
VP(0,201,200,-201)   SC(0,0,200,201)    -> draw#560 ev4712 img#23087
VP(0,768,1024,-768)  SC(0,0,1024,768)   -> draw#569 ev4762 img#3607
```

То есть viewport ставится под каждую цель (205², 256², 512×384, 256×192,
200×201, 1024×768) — **кроме** 2048². Перед ev54 действует значение,
поставленное для прохода 205×205→1024×768, и оно переносится на проход карты теней.

## События dxvk

Одиночный проход `vkCmdBeginRendering` area=`2048x2048` offset=`(0,0)`
(`passn` 29), **107 `vkCmdDrawIndexed`, 400 767 индексов, ev53 … ev522** —
тот же набор рисунков, что и у NVRHI (мультимножество `indexCount` совпадает 1:1):

```
ev53  vkCmdDrawIndexed indexCount=978 instanceCount=1
      pass ev… area=2048x2048 off=(0,0)
      VP (0.5, 2048.5, 2048, -2048)  SC (0, 0, 2048, 2048)   <-- верный размер цели
```

Вызов, который в NVRHI отсутствует:

```
vkCmdSetViewportWithCount  x=0.5 y=2048.5 width=2048 height=-2048
vkCmdSetScissorWithCount   x=0   y=0    width=2048 height=2048
```

## Возможная причина возникновения проблемы

NVRHI-слой D3D9 **не перевыставляет viewport/scissor при смене цели рендера на
2048×2048** (surface карты теней): он выставляет viewport под остальные цели
(205², 256², 512×384, 256×192, 200×201, 1024×768), а для прохода карты теней
использует то, что осталось от предыдущего прохода — 1024×768. Клиент при этом
`SetViewport(0,0,2048,2048)` вызывает: в DXVK-капче он доходит до Vulkan как
`vkCmdSetViewportWithCount(0.5, 2048.5, 2048, -2048)` ровно перед ev53.

Следствие: геометрия теней проецируется в прямоугольник 1024×768 внутри
2048²-изображения (сжатие 2× по X и 2.67× по Y относительно того, что делает
DXVK), а 3/4 карты остаётся нетронутой.

Проверка гипотезы выполнена так: viewport поправлен на размер цели, снята
повторная капча (`pw_frame2920`). Дефект карты закрыт (viewport 2048² появился),
но **к полосам на скриншоте это отношения не имеет** — полосы остались; разбор
полос — в начале документа и в `docs/PLAN_NVRHI.md`.

# Проблема 2. Полувитковый сдвиг viewport (D3D9 half-texel) не применяется нигде

## События Vulkan

Во **всех** проходах viewport без смещения:

```
VP(0,   205,   205, -205)   VP(0,   768,   1024, -768)   VP(0,   256, 256, -256)
VP(0,   384,   512, -384)   VP(0,   192,   256,  -192)   VP(0,   201, 200, -201)
```

## События dxvk

Во всех проходах (кроме финального blit-а) смещение +0.5 по X и Y:

```
VP(0.5, 205.5, 205, -205)   VP(0.5, 768.5, 1024, -768)   VP(0.5, 256.5, 256, -256)
VP(0.5, 384.5, 512, -384)   VP(0.5, 192.5, 256,  -192)   VP(0.5, 201.5, 200, -201)
```

Пара для примера: NVRHI `ev4558` (цель `img#172`, UI) `VP=(0,768,1024,-768)` ↔
DXVK `ev1948` (цель `img#246`, UI) `VP=(0.5,768.5,1024,-768)`.

### Ресурсы

Те же цели, что в Проблеме 1/3: `img#172`↔`img#246` BGRA 1024×768,
`img#170`↔`img#244` BGRA 1024×768 и т. д.; различается только прямоугольник
viewport.

## Возможная причина

D3D9 использует семплирование по центрам пикселей, и DXVK при трансляции
viewport добавает half-texel bias (+0.5), как того требует D3D9→Vulkan.
NVRHI этого смещения не добавляет. Следствие — сдвиг всей растеризации на полпикселя:
размытие/«мерцание» при билинейной фильтрации и текстурах, сдвиг краёв UI на
пиксель. К полосам из Проблемы 1 это отношения не имеет (период полос ~20 px),
но это систематическое расхождение A/B по всему кадру.

# Проблема 3. Утерян load-op CLEAR: все аттачменты LOAD, явных clear'ов 7 на кадр

## События Vulkan

На каждый из 467 проходов все аттачменты — `ATTACHMENT_LOAD_OP_LOAD` /
`STORE`. Единственные clear'ы — отдельные команды:
`vkCmdClearColorImage` ×3, `vkCmdClearDepthStencilImage` ×4 (например clear
`img#36422` выполняется вне прохода карты теней).

```
ev54 pass: C view#36431 img#36424 LOAD/STORE ; D view#36432 img#36422 LOAD/STORE
```

## События dxvk

Clear задаётся самим load-op прохода:

```
ev53 pass: C view#12891 img#11920 LOAD/STORE
           D view#12892 img#11914 CLEAR value=(1,0,0,0) /STORE
           S view#12892 img#11914 CLEAR value=(1,0,0,0) /STORE
ev570 pass (цель сцены): C img#244 CLEAR (0,0,0,0) ; D/S img#240 CLEAR (1,0,0,0)
```

Всего в DXVK: 3 color-CLEAR + 4 depth-CLEAR + 3 stencil-CLEAR в load-op,
ноль отдельных clear-команд.

### Ресурсы

Одни и те же изображения (`img#36422`↔`img#11914`, `img#170`↔`img#244`,
`img#166`↔`img#240`), different — способ инициализации.

## Возможная причина

NVRHI всегда ставит `LOAD`, а сброс выполняет отдельными
`vkCmdClearColorImage`/`vkCmdClearDepthStencilImage` вне проходов. Там, где
DXVK гарантированно обнуляет цель перед первым рисунком (карта глубины теней —
`(1,0,0,0)`, сцена — `(0,0,0,0)`), NVRHI приносит старое содержимое. В
сочетании с Проблемой 1 это означает, что 3/4 карты теней, не закрытые
растеризацией, содержат **старые данные**, а не «пустую» глубину.

## Развязка (2026-10-25, синхронная пара)

Опасение про «3/4 карты теней со старыми данными» **не подтвердилось** — оно и в
прошлой пачке было опровергнуто разделом «Полосы». На синхронной паре: NVRHI
делает 3 color-clear + 7 depth/stencil-clear отдельными командами, DXVK — 0
отдельных (все 10 в load-op). Набор обнуляемых целей тот же; карта теней целиком
перекрывается проходом глубины, сцена — 8935 рисунками. **Дефекта обнуления
нет.**

Пункт остаётся только как задел на производительность и чинится вместе с
Проблемой 4: clear в load-op убирает по одному проходу-заливке на цель
(`Vendor/NVRHI/src/vulkan/vulkan-graphics.cpp:80-81,111-112` жёстко ставят
`eLoad/eStore`; там же `createFramebuffer` не знает, что цель только что
обнулили). Правка вендорская, без поведенческого гейта — отложена на батчинг
выводов.

# Проблема 4. Проход рендера открывается на каждый рисунок (467 против 33)

## События Vulkan

467 пар `vkCmdBeginRendering`/`vkCmdEndRendering`; внутри, как правило, **один**
`vkCmdDraw*`, между проходами — `vkCmdPipelineBarrier2` и `vkCmdUpdateBuffer`.
Пример подряд идущих: `ev1587 BeginRendering → ev1592 DrawIndexed → ev1593
EndRendering → ev1594 barrier → ev1595 UpdateBuffer`. Всего
`vkCmdPipelineBarrier2` = **1214**.

## События dxvk

33 прохода, в каждом пачка рисунков (например `passn` 29 — 107 рисунков карты
теней, `passn` со start `ev3232` — 89 рисунков UI). Всего
`vkCmdPipelineBarrier2` = **46**.

### Ресурсы

Те же цели; различие — только в гранулярности проходов и числе переходов
layout/barrier.

## Возможная причина

D3D9-слой NVRHI считает каждое изменение состояния границей subpass. Следствие —
полный load/store больших целей (2048², 1024²) на каждый рисунок и 26× больше
барьеров. Это не только потеря производительности: при `LOAD`-повсеместности
(Проблема 3) каждый такой проход — ещё одна возможность принести старое
содержимое вместо clear'а.

## Развязка (2026-10-25, синхронная пара)

Подтверждено и усилено: на обзорном кадре **13 220 пар Begin/EndRendering
против 47** и **25 654 `vkCmdPipelineBarrier2` против 99** (274×). Механизм тот
же: `Vendor/NVRHI/src/vulkan/vulkan-buffer.cpp:464` при `writeBuffer` вне вывода
закрывает проход (`endRenderPass`), следующий рисунок открывает новый.

Это единственный из оставшихся пунктов, который прямо упирается в
производительность Vulkan-контура (под слоем он и так едет ~20 fps против ~97 у
DXVK). Правка не seam'овая, а вендорская (NVRHI Vulkan: не рвать проход ради
upload, либо держать проход открытым до смены цели) — в очереди плана это
«батчинг выводов», не закрывалось в этой пачке.

Замер частоты кадров **без слоя** (один и тот же exe, `PW_FPS_STATS=30` →
`Renderer::Present`, `Render/renderer.cpp:986` — счётчик стоит в общей точке обоих
бэкендов, поэтому Δ сравнимо; обзорная камера статична, 150 с, канонический
`ab_user.cfg`): интервалы по 30 с — Vulkan `10,23 / 6,46 / 0,82 / 0,83`,
D3D9+DXVK `33,86 / 1,55 / 1,55 / 1,56` (первый интервал — экран загрузки).
То есть на draw-тяжёлом кадре (13 220 выводов) Vulkan-контур **~1,9× медленнее**
DXVK (0,82 против 1,55 fps) — что согласуется с 274× барьеров и 282× проходов.
В обычной камере тот же билд даёт ~30 fps (`VkSum: presents=3599` за ~120 с),
значит цена именно в числе выводов/проходов, а не в самом Vulkan. Частоты
Vulkan-прогона деградируют от интервала к интервалу (10,23 → 6,46 → 0,82), у
DXVK стабильны; виртуальная памяти 2383 МБ против 1408 МБ. Причина деградации
не установлена — отдельная задача.

Двусмысленно, требует проверки:

1. **Разница моментов съёмки.** Кадры 2314 и 9105 — не один и тот же момент

2. **Потеря рисунков в NVRHI.** Косвенный признак: во всём кадре NVRHI **нет ни

   25 различных декларациях. Но pipeline создаётся лениво, так что это
   доказательством не является.

Диагноз возможен только на **синхронной паре** (одинаковый игровой момент,
одинаковая поза камеры, одинаковый HP). Индикатор: появляется ли в NVRHI
pipeline с декларацией `pos3@0;BGRA@12;BGRA@16;RGBA32F@20` и рисунки с
`indexCount ∈ {3846, 801, 1728, 3444, 2178, 567, 2490, 1776, 1200, 1620, 684}`.

## Развязка (2026-10-25, синхронная пара)

Индикатор сработал: на синхронной паре **10 из 11** `indexCount'ов` этого блока
в NVRHI есть — 67 рисунков против 86 у DXVK, те же классы (`2178`×19 в сцене и
в картах теней, `1200`×8, `567`, `3444`, `1728`…). То есть сам пропущенный блок
был артефактом несинхронной съёмки (Проблема 6), а не потерей рисунков.

Но дефицит рисунков у Vulkan-контура реален и лежит в другом классе —
`cnt=264 inst=1` (−1476 рисунков, см. «Третью пачку»). Причина по логам:

- `ShaderTarget: Shaders/UberShaders/<материал> #<индекс> — комбинации нет в
  цели, нужен рантайм-компилятор` — **27 уникальных** пар: `BasicMaterial` 14,
  `ParticleFXMaterial` 5, `BasicFXMaterial` 4, `TerrainElementMaterial` 3,
  `DropMaterial` 1 (лог сессии, счёт по `rdcap_shaderfail.py`);
  плюс 69 «бэкенд цель ещё не умеет» (SM3-фолбэк).
- шейдер не создан → ручка нулевая → `SetVertexShader — пустая ручка` (6) →
  `Вывод: нет VS (не выставлен или чужой)` (12). Счётчик `drawSkipVs` в прогоне
  без слоя — 0, то есть основную массу объектов с мёртвым материалом приложение
  **не выпускает в бэкенд вообще**, и в капче их нет.
- у DXVK тот же клиент собирает все варианты (SM3-DXBC-слой в контейнере полный),
  поэтому там эти объекты рисуются.

Пиксельное следствие (обзор, 110 с, контроль — `main` с читаемой глубиной,
`DepthFormat: INTZ`, т.к. DXVK отвечает «да» на INTZ):
`main`(INTZ) ↔ NVRHI/Vulkan = mean\|d\| **6.71**, diff>8 **26.11 %**, gross>64
**13.0 %**; для сравнения `main`(rd0) ↔ NVRHI/d3d9 = 0.99 / 2.24 % / 0.01 %
(Проблема 12). Карта различий `/tmp/diff_ovw_vk_vs_mainINTZ.png`: яркие
«штрихи» по границам тайлов и построек (пропущенная геометрия), ровное плато
внутри квада тумана, тонкий контур арены; чёрных дыр-тайлов нет.

Чем закрывать (в порядке возрастания цены, оба пути уже в плане):

1. пересобрать SPIR-V-секцию контейнеров под живой набор индексов этой сцены:
   `setvar dump_shader_index 1` → `tools/shader_build/collect_live_indices.py`
   → `tools/shader_build/mkshd2.py --live <merged.json> --materials
   BasicMaterial,ParticleFXMaterial,BasicFXMaterial,TerrainElementMaterial,
   DropMaterial` (DXC нативный, `vendor/dxc/bin/dxc`); **но** контейнеры лежат в
   контенте (`Game/Packs/*.pile`), значит это правка контентного репозитория и
   прод-действие — в этой пачке не выполнялось;
2. рантайм-компилятор HLSL→SPIR-V (решение плана §3.z п.3 «вариант (1)» —
   прекомпилировать всё пространство `BasicMaterial` нельзя: 1 144 128 Б на

## Развязка (2026-10-25, вариант 1 выполнен на стенде)

Закрыто пересборкой SPIR-V-секции под живой набор индексов. Прод-контент **не
тронут** (ни коммита, ни push): репозиторные контейнеры в `pw/branches/r1117/Data/
Shaders/UberShaders/` оставлены как были, пересобранные файлы лежат рядом со
стендом — `~/PW/wine-client-nvrhi/shaders-2026-10-25-p5/` (5 `.shd` +
`live_indices-2026-10-25-captures.json`), на стенд доставлен отдельным пайком
`wine-client-nvrhi/Game/Packs/zpatch_shaders.pile` (183 571 Б, 5 контейнеров) —
`ScanForPiles` грузит `*.pile` по алфавиту, `z…` перекрывает `gamedata073.pile`.

Живые индексы собраны не генератором, а по капчам: `dump_shader_index 1` даёт
строки `ShaderIndex: <материал> #<индекс>`, но `dumpShaderIndex` включается
только с `shader_target != 0` (`Render/multishader.cpp:157-172`), а `shader_target`
не читает `autoexec.cfg` (`ConfigManager.cpp:110` вызывается раньше
`LoadAutoExecFile`), поэтому пины выставляются **командой чата** в раннем окне
загрузки; индекс берётся из XML-дампа капчи (`tools/rd/rdcap_liveidx.py`,

сделана без этого флага: мир исчез (остались только квад тумана, силуэт героя и

канонической раскладке, константы уходят не туда, геометрия не трансформируется.

5815`, `4607`). Контроль регресса после правки: побайтово совпали все ранее
живые блобы (`BasicMaterial` 42/42, `TerrainElementMaterial` 16/16,
`ParticleFXMaterial` 4/4, `BasicFXMaterial` 14/14); у `DropMaterial` совпало
0/5 — канонический банк строится по **множеству** компилируемых индексов,
поэтому добавление 140-го перетасовало банк и пересобрало соседние блобы
(самологично: контейнер целиком пересобран, клиент берёт раскладку из блоба).

Что дали новые варианты:

- `нужен рантайм-компилятор` — **0** (было 27 уникальных), `цель … не создана` — 0;
- обзорная камера `main` ↔ NVRHI/Vulkan: diff>8 **26,11 % → 21,75 %**, mean\|d\|
  **9,83 → 7,27** (стабильно на 60/85/110/135 с), gross>64 1,77 %;
- счётчик дыр террейна (`frame_ab.py holes`, связные почти-чёрные компоненты
  ≥400 px) стал **идентичен** `main`: 1 компонент 31 913 px (у битого пайка —
  2 компонента 37 319 px);
- обычная камера **не изменилась**: mean\|d\| 35,41/36,92/35,11 → 36,05/36,84/35,57
  на 70/95/120 с. То есть расхождение тона обычной камеры (см. «Четвёртую
  пачку») к отсутствующим вариантам отношения не имеет.

Остаток открытым: дублировать набор в прод-контент (`UpdateRepos/content_pwc`,
`Game/Packs/*.pile`) — прод-действие, не выполнялось; и шаг 14 (рантайм-DXC)

# Проблема 8. Финальный композит: разная длина цепочки и разный формат swapchain

## События Vulkan

Один полный экран: `ev4762 vkCmdDrawIndexed cnt=6`,
`C view → img#3607` (**B8G8R8A8_UNORM**), load=`LOAD`,
VP `(0,768,1024,-768)`, pipeline `37666`. Источник — `img#172` (UI-цель).
`vkQueuePresentKHR` без дополнительного blit-а.

### Ресурсы

`img#3607` — swapchain image, формат `B8G8R8A8_UNORM`; читаемая цель `img#172`
BGRA 1024×768, 204 рисунка до этого.

## События dxvk

Два шага:

```
ev3837 vkCmdDrawIndexed cnt=6  C img#199 (BGRA_UNORM) LOAD   VP(0.5,768.5,1024,-768)  pipe#11716
ev3863 vkCmdDraw       cnt=3   C img#392 (BGRA_**SRGB**) DONT_CARE  VP(0,0,1024,768)  pipe#420
```

`vkCmdBlitImage2` ×1 в кадре.

### Ресурсы

`img#199` BGRA 1024×768 (промежуточная), `img#392` swapchain
**B8G8R8A8_SRGB**. По инвентарю изображений: у DXVK 3 изображения
`B8G8R8A8_SRGB` и 4 `R16G16B16A16_SFLOAT`, у NVRHI — **ни того ни другого**
(все BGRA у него UNORM).

## Возможная причина

DXVK ведёт present через отдельный blit в sRGB-swapchain (аппаратное
линейно→sRGB преобразование на записи), NVRHI рисует прямо в UNORM-swapchain
без преобразования и без Y-инверсии в последнем проходе (`VP(0,0,1024,768)` у
DXVK-блина против `VP(0,768,1024,-768)` у NVRHI). Если где-то в цепочке кадр
оказывается в линейном пространстве, форматы дают разную яркость/гамму.
К полосам отношения не имеет, но это расхождение цвета A/B, которое надо
зафиксировать до визуальной сверки кадров.

## Развязка (2026-10-25)

**На картинку не влияет** — замер по кадрам обзора (NVRHI/Vulkan ↔ `main` с
читаемой глубиной, одна и та же сцена, области вне арены — равномерная заливка
туманом, где никакой геометрии нет):

| область | NVRHI/Vulkan | `main`(INTZ) |
|---|---|---|
| пустота, левый верхний угол | R 9.42 G 16.33 B 30.14 | R 9.42 G 16.33 B 30.14 |
| пустота, правый нижний угол | R 15.00 G 26.00 B 48.00 | R 15.00 G 26.00 B 48.00 |
| центр уровня | R 83.79 G 82.71 B 78.67 | R 60.10 G 66.06 B 69.88 |

Финальный композит даёт **побитово одинаковые байты** при `B8G8R8A8_UNORM`
против `B8G8R8A8_SRGB`: игра пишет в swapchain уже готовые для дисплея значения,
а сам swapchain никто не сэмплирует (у NVRHI в кадре нет ни одного blit и ни
одного рисунка, читающего swapchain-image). Разница формата и лишняя ступень
композита у DXVK (`img#199` → `img#392` SRGB, `vkCmdBlitImage` ×1) — внутреннее
дело DXVK, не расхождение цвета.

Расличие в центре уровня (R +23.7, G +16.7, B +8.8) — это не гамма, а
пропущенная геометрия/материалы Vulkan-контура: см. Развязку Проблемы 5.

# Проблема 10 (критическая). Читаемая глубина на D3D9-бэкенде в D24S8 → туман войны ложится на вьюпорт

Наблюдение (по кадрам, не по капче): на обычной камере кадр `nvrhi`/d3d9 под
Wine+DXVK залит сине-серой пеленой по всему вьюпорту — `B−R = +26.3`, уникальных
цветов 459 против 1791 у `main`. При `setvar readableDepthEnable 0`
(`Render/ConfigManager.cpp:297`, `REGISTER_VAR`, `STORAGE_NONE`) кадр совпадает с
`main` в масштабе шума анимации.

| кадр (обычная камера, NOUI=1, 150 с) | mean | B−R | uniq |
|---|---|---|---|
| `main`/DXVK | 79.58 | −4.7 | 1791 |
| `nvrhi` d3d9, база | 67.83 | **+26.3** | 459 |
| `nvrhi` d3d9, `readableDepthEnable 0` | 81.30 | −5.7 | 1556 |

| пара | gross>64 | diff>8 | mean\|d\| |
|---|---|---|---|
| `main` ↔ `nvrhi` d3d9 база | 10.40 % | 92.51 % | 35.16 |
| `main` ↔ `nvrhi` d3d9 rd0 | 1.70 % | 15.98 % | 6.69 |

## Код

- `main`: `Render/ConfigManager.cpp:231` — `ReadableDepthSupported() = caps &
  (hasRAWZ|hasINTZ) || AllowDF24(caps) || …`; `:244-246` —
  `GetDepthFormatPreffered()` → `FORMAT_INTZ`, лог `DepthFormat: INTZ`.
- `nvrhi`: `Render/ConfigManager.cpp:241-248` — `caps & (hasD16T|hasD24X|hasD24S)`;
  `:259-262` — всегда `FORMAT_D24S8`, лог `DepthFormat: D24S8`. Vendor-форматы
  удалены коммитом `a639d8319`.
- Потребитель: `PF_GameLogic/PFRenderInterface.cpp:397-415` (`CreateDepthTextures`:
  `pMainDepth` D24S8 + `depthCopyShaderName = "DecodeZ"`); единственный читатель
  `ReadableDepthEnabled()` — `PFRenderInterface.cpp:1828`. Пост-проход —
  `Shaders/FullScreenMaterial.hlsl:236-244`:
  `warfogMapping = BasePos + z*Texcoord.zw`, `z = tex2D(DepthMap, Texcoord).r`.

## Возможная причина

Под D3D9 семантикой depth-поверхность можно **сэмплировать** только
vendor-форматом (INTZ/RAWZ); D24S8 как color/depth SRV под DXVK даёт неверные
отсчёты глубины → неверный `warfogMapping` → туман ровной пеленой по вьюпорту
вместо террейна. Комментарий `ConfigManager.cpp:242-245` («под Vulkan/DX12
depth-буфер читается как depth SRV всегда») верен для Vulkan/DX12 и **ложен для
D3D9** — а D3D9 на ветке остаётся путём по умолчанию: `Render/renderer.cpp:501-507`
`backendOn = requestVulkan || (!requestD3D9 && envOn)`, Vulkan только по токену
`render=vulkan` или env `PW_VK_BACKEND`.

Не подтверждено по пикселям, что именно возвращает D24S8-SRV под DXVK: DXVK-капчу
прохода `DecodeZ` хостовым слоем не взять (winevulkan вне цепочки загрузчика).
Доказательство поведенческое — ручка + лог формата + спецификация D3D9.

Где править: `ReadableDepthSupported()` / `GetDepthFormatPreffered()` — на
D3D9-бэкенде не считать `hasD16T/hasD24X/hasD24S` признаком читаемой глубины
(требовать `hasRAWZ`/`hasINTZ`, как в `main`), D24S8 оставить за NVRHI-бэкендами.
Нужен предикат активного бэкенда: в `renderer.cpp` он есть (`bVkBackend`, лог
`backend=vulkan|d3d9` на `:1020`), наружу не выведен. Винный гейт `main`
(`main/ConfigManager.cpp:39`) возвращать нельзя — он маскирует, а не лечит.

## Закрыто (2026-10-25): бит `hasDepthSRV`

Предикат бэкенда наружу не выводили (как предлагал `bVkBackend`) — вместо этого
введён **бит возможности**, который выставляет только NVRHI-бэкенд:

- `Render/Features.h`: `hasDepthSRV = hasD24S << 1` (бит 8), `featuresVersion`
  2 → 3 (набор флагов изменился несовместимо, отчёты носят маску `caps`).
- `Render/nvrhibackend.cpp:3322` (`NvrhiBackend::GetSystemInfo`) — ставит
  `hasDepthSRV` рядом с `hasD16T/hasD24S`, которые считает по
  `vkGetPhysicalDeviceFormatProperties` (D16/D24_UNORM_S8/D32_SFLOAT_S8).
- `Render/d3d9backend.cpp:53-62` (`D3D9Backend::GetSystemInfo`) — `hasD16T/…`
  считает как раньше (`CheckDeviceFormat` D16/D24X8/D24S8), `hasDepthSRV` **не
  ставит**: под D3D9 depth-текстуру сэмплирует только vendor-формат
  (INTZ/RAWZ), а они удалены коммитом `a639d8319` и возвращаться не должны
  (план, §зачистка D3D9).
- `Render/ConfigManager.cpp:241-248` — `ReadableDepthSupported()` требует
  `hasDepthSRV`; `GetDepthFormatPreffered()` не трогали (он и так вызывается
  только когда читаемая глубина включена).

Почему это не регрессия картинки: при выключенной читаемой глубине включается
штатный путь `DoDepthOut` — `PF_GameLogic/PFRenderInterface.cpp:1501`
`GetRuntimePins().DoDepthOutValue = s_readableDepth ? BOOLPIN_FALSE : BOOLPIN_TRUE`,
то есть глубина экспортируется в color-RT (R32F) и туман войны считается по ней.
Это тот же путь, которым на проде идут машины без INTZ — а не заглушка.

Диагностические строки (остались в коде, они и есть гейт проверки):
`Readable depth: on|off (caps=0x…)` после разбора `caps` в `ConfigManager.cpp`.
Замер по логам сессий: d3d9-контур — `Protocol render backend: "d3d9"`,
`Readable depth: off (caps=0x5)`, строки `DepthFormat:` нет; Vulkan-контур —
`Readable depth: on (caps=0xd)`, `DepthFormat: D24S8`.

Пиксельная проверка (обзор, margin 0.18, NOUI=1, 4 кадра 60/85/110/135 с):
`main` с `readableDepthEnable 0` ↔ NVRHI/d3d9 = mean\|d\| **0.99**,
diff>8 **2.24 %**, gross>64 **0.01 %** на всех четырёх кадрах. Прежняя пара этой
же проблемы давала 64.58 (средняя яркость пелены) и 2.03 / 6.19 % в обзоре.

Важная поправка к «Методике» ниже: `main` под этим Wine печатает
`DepthFormat: INTZ` (лог 2026.10.25-02.03.31), то есть DXVK отвечает «да» и на
INTZ — `main`-под-Wine работает с читаемой глубиной **включённой**, конфигурации,
которой прод не видит. Поэтому честный контроль D3D9 — `main` c
`setvar readableDepthEnable 0`, как и требует «Методика».

## Закрыто (2026-10-25): тот же гейт + маппинг `bfD16`

Формат глубины карты теней выбирается по возможности, а не жёстко (`ShadowMap.cpp`,
`ShadowMapPCF_DS::Init`):

```cpp
D3DFORMAT format = pConfigManager->HasDepthSRV() ? D3DFMT_D24S8
                 : (pConfigManager->HasD24X() ? D3DFMT_D24X8 : D3DFMT_D16);
```

Это ровно то, что делал `main` (`main/Render/ShadowMap.cpp:199`), а не отключение
пути аппаратных карт: `HasDSM()` оставлен как есть, DSM-проход жив, просто под
D3D9 он берёт D16 (или D24X8, если бэкенд его разрешает). Уточнение к тексту
проблемы: в `main` этот проход **тоже сэмплирует** глубину
(`SetSampler(1, …, pDepth)` в `ShadowMapPCF_DS::Apply`) — отличался формат, а не
наличие SRV.

Попутно найдена и исправлена **собственная регрессия**, которую эта правка
обнажила: `D3DFMT_D16` отсутствовал в словаре форматов seam'а
(`Render/renderbackend.h`, `SurfaceFormat`), поэтому после перехода на D16
call `SetRenderTarget` падал и **проход карт теней под D3D9 не создавался
вовсе** (в капче `pairB_dx` цели 2048×2048 нет вообще, в `pairC_dx` — есть,
7399 рисунков). Добавлены `bfD16` в enum (`BACKEND_FORMAT_COUNT` 18 → 19) и его
маппинг в таблицах `nvrhibackend.cpp`.

Диагностика в коде: `ShadowMap: PCF_DS, depth D24S8|D16` и
`ShadowMap: PCF (MRT), DSM недоступен`. Замер: d3d9-контур —
`ShadowMap: PCF_DS, depth D16`; Vulkan-контур — `ShadowMap: PCF_DS, depth D24S8`.

Вклад в картинку по-прежнему не измерен (в сцене спавна тени не измеримы), но
проверено, что после правки D3D9-контур совпадает с `main` на обзоре
(0.99 mean\|d\|, см. Проблему 12) и что проход карт теней в капче присутствует.

# Методика: почему дефект проявился только под Wine

- DXVK отвечает «да» на `CheckDeviceFormat(D24S8, DEPTHSTENCIL, TEXTURE)`,
  реальное D3D9-железо — нет (замер на tiny10, «Microsoft Basic Render Driver»:
  `no` для D16/D24X8/D24S8, реальная попытка `CreateTexture` → `0x8876086C`,
  `tools/dsm_probe`, `docs/PLAN_NVRHI.md §2.15 п.9`). На Windows эти пути не
  включаются вообще, поэтому регрессия от зачистки vendor-форматов там невидима.
- Следствие для A/B: Wine/DXVK-контур включает конфигурацию, которой прод не
  видит. Контроль D3D9 надо фиксировать в конфигурации реального железа
  (`readableDepthEnable 0`, `force_dsm` не включать) и сверять с tiny10, иначе
  A/B сравнивает не то, что поедет пользователям.
- `main` под этим Wine **не** печатает `System runned under Wine` — винный гейт
  `main/ConfigManager.cpp:39` не срабатывает, читаемая глубина включена на обоих
  стволах; различие только в формате (Проблема 10).
- Конур проверять по строке сессии `Protocol render backend: "…"`: в
  `run_overview.sh` nvrhi-стенда по умолчанию `BACKEND=vulkan`, и часть прогонов
  этой серии была Vulkan вместо d3d9.

# Что различается, но дефектом не является

Чтобы не гонять эти пункты повторно:

- **Depth/stencil-аттачмент отсутствует у 198 рисунков NVRHI** (`img#172` — 173,
  `img#23087` — 9, `img#170` — 6, прочие — по 1–2), там где DXVK всегда несёт
  `D#213`/`S#213`. Проверено по pipeline: у **всех** этих рисунков
  `dtest=0 dwrite=0 stest=0` — глубина не нужна, аттачмент правомерно опущен.
- **109 pipeline у NVRHI против 70 у DXVK** — NVRHI запекает состояние в
  pipeline, DXVK делает depth/stencil/cull/viewport динамическим
  (`DYNAMIC_STATE_*` + 96×`vkCmdSetStencilOp`, 83×`vkCmdSetCullMode`,
  28×`vkCmdSetDepthTestEnable`). Сравнивать надо **эффективное** состояние на
  рисунке, а не статику pipeline.
- **Способ записи дескрипторов**: NVRHI — 123 статических set'а и 525
  `vkCmdBindDescriptorSets` + 711 `vkCmdUpdateBuffer`; DXVK — 322 364
  `vkGetDescriptorEXT` + `vkCmdSetDescriptorBufferOffsets2EXT`. Разные
  стратегии, не расхождение.
- **`img#36424` имеет `SAMPLED`, `img#11920` — нет.** Разница в флагах создания,
  при `colorWriteMask=0` без последствий.
